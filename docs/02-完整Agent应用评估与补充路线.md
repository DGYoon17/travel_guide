# 作为完整 Agent 应用开发项目的评估与补充路线

> **历史文档（采购版）**：本文的成熟度评估与路线图针对采购域。差旅主线的实现与评测见
> [04-差旅Agent改造说明.md](04-差旅Agent改造说明.md)。

> **原始问题**：如果把这个项目做成一个完整的 Agent 应用开发项目，它有哪些已经具备的优点和需要完善的补充点？
>
> 评估对象：ProcureMind AI（完成记忆与 Harness 改造后的状态）
> 评估时间：2026-08-20
> 代码规模：`app/` 9254 行 / 82 个模块，`tests/` 2142 行 / 112 个测试

---

## 一、评估框架

一个"完整的 Agent 应用开发项目"至少要在 12 个维度上站得住。先给结论，再逐条展开。

| # | 维度 | 成熟度 | 一句话判断 |
|---|---|---|---|
| 1 | Agent 核心循环 | ★★★★☆ | 原生 function calling + 真流式 + 错误闭环，主干扎实 |
| 2 | 记忆与状态 | ★★★★☆ | 六层分层且按错误代价划分，L4 未接线 |
| 3 | 安全与权限 | ★★★★☆ | 身份不可伪造、scope 分级、租户隔离；缺出站脱敏与限流 |
| 4 | 可靠性与降级 | ★★★★☆ | 四重预算 + 规则兜底 + 熔断；缺重试策略与分布式协调 |
| 5 | 领域建模 | ★★★★☆ | 制度与审批链单一真相，金额单调性有测试；制度是硬编码 |
| 6 | 质量保障 | ★★★☆☆ | 112 测试 + 金标门禁；缺模型在环评测与对抗测试 |
| 7 | 可观测性 | ★★★☆☆ | trace_id 贯通、metrics/audit 端点；指标是进程内的，不可聚合 |
| 8 | 检索与知识 | ★★☆☆☆ | 有审核态与注入防护；但 RAG 与主链路未真正贯通，无引用溯源 |
| 9 | 工程基建 | ★★☆☆☆ | 有容器化与 pyproject；**无 CI、无迁移工具、12 个死代码模块** |
| 10 | 成本与配额 | ★☆☆☆☆ | 有单请求 token 预算；无按租户核算、无配额、无多供应商路由 |
| 11 | 领域集成 | ★☆☆☆☆ | 下游全是进程内模拟，无契约测试、无审批状态回调 |
| 12 | 交付与体验 | ★☆☆☆☆ | SSE 协议设计完整但**无消费方**；无前端、无 SDK、无会话列表 |

**总体判断**：这是一个 **Agent 后端内核已经相当成熟、但产品化与工程化外围明显偏薄** 的项目。它的强项恰好是最难做对的部分（状态治理、写操作治理、错误闭环、身份边界），弱项集中在"接上真实世界"和"团队协作可持续"这两块。

## 二、已经具备的优点

### 2.1 Agent 核心循环设计得住（★★★★☆）

**优点**

- **用原生 function calling 而非自研 ReAct 文本解析**。这是关键取舍：`_parse_step` 那类 JSON 提取在生产里失败率高且难归因，原生 `tool_calls` 由服务端结构化返回。
- **真流式且中间态可见**。`stream_turn` 按 `index` 累积 `tool_calls` 分片，SSE 分 `status` / `tool_call` / `tool_result` / `content` / `confirmation_required` / `done` / `error`。采购一次请求可能跑 3–4 轮工具，用户能看到"正在校验采购制度…"而不是空白屏。
- **工具错误反馈闭环**。这是最能体现 Agent 工程理解的一处：参数校验失败不是 500，而是带 `field_issues{field, problem, expected, example}` 的结构化观察值回喂模型；`REPAIRABLE_CODES` 区分"值得让模型再试"与"必须立即停"。
- **宽松解析优先于报错**。`下周五`、`3个工作日后`（跳周末）、`1.5万`、`18,800元` 直接解析成功，而不是先失败一轮再让模型改。这才是真正降低失败轮次的做法。
- **风险分级 + 只读工具并发**。`READ` / `DRAFT` / `WRITE` 三级，只读工具 `asyncio.gather` 并发（改造前是顺序 for-await）。
- **单一真相**：`ToolSpec` 一份声明同时驱动 schema、校验、注入、权限、超时、确认门。

**可作为方法论复用的点**：把"工具错误"当成 Agent 的一等公民设计，而不是异常处理的边角。

### 2.2 记忆分层按"错误代价"而非"时间远近"（★★★★☆）

**优点**

- 六层 L0–L5 的划分依据是**记错的后果有多严重**，这在有合规后果的业务里是正确的切法。
- **L2 槽位记忆**把多轮正确性从"模型的记忆力"转移到"服务端状态"：每个槽位记来源（user/inferred/master_data/tool）与是否已确认；`confirmed=True` 禁止静默改写，被拒绝的变更留痕并回灌进 system prompt 提示模型。
- **L1 的三个结构性修复**（摘要移入不可裁剪的 pinned 区、裁剪单位改消息组、token 增量计数）不是打补丁，而是让原问题**物理上不可能再发生**。
- **摘要的数字可追溯**：摘要里的每个金额/日期必须能在对话原文或 L2 草稿中溯源，否则丢弃并告警。这直接对冲了"15000 被压成约 1.5 万再被读成单价"这类幻觉链。
- **L5 事实日志与对话记忆分离**：会被摘要压缩的东西和需要审计的东西不能是同一份数据。
- **L3 身份从凭据来**，模型看不到也改不了——同时解决了功能问题（用户不用每轮重复交代）和安全问题（不能冒用身份）。

### 2.3 写操作治理是同类项目里少见的完整（★★★★☆）

**优点**

- 确认门**不由 LLM 也不由正则**决定：模型调用 WRITE 工具时只登记 `PendingAction`，执行必须走独立接口带 `action_id`。
- 回给用户的确认摘要是**确定性拼装**的，反思阶段只允许追加风险提示、不允许改写数字——用户确认的和实际提交的必然是同一份。
- 幂等键 = 租户+主体+请购单 ID+草稿内容指纹；审批单号由幂等键确定性派生，重复确认返回同一单号。
- 确认前草稿被改过 → 指纹不符 → 409 拒绝重新生成。这个细节很多实现会漏。
- 全链路留痕：`ACTION_PENDING` → `ACTION_CONFIRMED`/`REJECTED`/`REPLAYED` → `APPROVAL_SUBMITTED`。

### 2.4 降级路径是真降级，不是兜底文案（★★★★☆）

**优点**

- 采购场景恰好有确定性兜底可用：`RuleEngine` 是纯正则、制度阈值与审批链是纯函数。LLM 挂了仍能回答"8000 元以上软件采购需三家报价 + 信息安全评估"并给出完整审批路径，且明确标注为降级。
- **预算触顶不等于白跑**：用已有工具产出 best-effort 收尾，保留请购单内容与缺失项追问。
- 熔断器补了 `record_external_failure()`——流式失败发生在 `breaker.call()` 之外，没有这个入口阈值形同虚设。
- Redis / PostgreSQL / Milvus 各自不可用时显式降级并告警，`/health` 如实反映（不再把"未连接"报成健康）。

### 2.5 领域建模与不变量测试（★★★★☆）

**优点**

- 审批链只有一份真相：`policy_query` 改为委托 `build_default_approval_path`，制度校验与请购单生成必有相同结果，并有测试锁定这条不变量。
- 金标集里有**金额单调性测试**：金额变大时审批节点只能增加不能减少。阈值配错时这条最先炸，是很有效的守卫。
- 合规漏报零容忍（`MIN_COMPLIANCE_RECALL = 1.0`）——漏报比误报危险得多，阈值方向定对了。
- 金标集有"防缩水"测试，阻止有人删用例让门禁通过。

### 2.6 测试与评测思路正确（★★★☆☆）

**优点**

- 112 个测试**围绕已知失效模式**写，不是为覆盖率而写：每个测试的 docstring 都说明"改造前会怎么错"。
- 金标评测拆成四个可量化指标并阈值化，可直接当 CI 门禁。
- 金标集诚实：意图准确率 90.91% 而非人为凑到 100%，那一例失败（「公司内部的报销制度手册在哪」→ `info_query` 而非 `rag`）被记录下来而不是改断言掩盖。
- `FakeLLM` 夹具可按脚本回放多轮工具调用，端到端测编排器不需要真实模型。

### 2.7 其它工程细节

- 配置项集中且有注释说明约束关系（如"`memory_summary_trigger_tokens` 必须小于 `memory_max_tokens`，否则窗口先裁剪、摘要永不触发"）
- 业务时区抽成 `core/clock.py` 并在 tzdata 缺失时回落固定 +08:00
- embedding 维度与 collection 维度强绑定并提前校验，不等到写库才报错
- 间接 prompt injection 防护：检索内容包在 `<knowledge>` 数据边界内、剥离伪造边界标签、可疑文档标记、知识库写入与发布权限分离
- Dockerfile 非 root、docker-compose 环境变量名与代码一致

## 三、需要补充与完善的点

按"不补会出事"的紧迫程度分类。

### A 类：工程基建（最薄的一环，直接影响可持续性）

#### A-1 没有 CI 配置文件 —— 门禁没有执行载体 🔴

**现状**：写了金标评测和阈值门禁，但仓库里没有 `.github/workflows/`（或任何 CI 配置）。

**影响**：门禁不会自动跑，等于把守卫写好了没上岗。改 prompt 或改规则导致的退化仍然只能靠人记得跑 `pytest`。

**建议**：加 `.github/workflows/ci.yml`，至少三个 job：
```yaml
lint:   ruff check + ruff format --check
type:   mypy app（先 --ignore-missing-imports，逐步收紧）
test:   pytest --cov=app --cov-report=term --cov-fail-under=70
gate:   pytest tests/test_golden_eval.py -v   # 单独 job，失败信息更醒目
```
另外 pyproject 里配了 `[tool.ruff]` 但从未执行过，`mypy` 配置完全没有。

#### A-2 12 个模块已成死代码 🔴

改造后经完整 import 扫描确认，以下模块**无任何引用**：

| 模块 | 状态 | 备注 |
|---|---|---|
| `app/core/agent/react_agent.py` | 死 | README 曾把 ReAct 当亮点 |
| `app/core/agent/planner.py` | 死 | `enable_planner` 配置项存在但无消费点 |
| `app/core/agent/reflection.py` | 死 | **写操作自检用 `LLMService.complete` 直接实现，没复用它** |
| `app/core/prompt/templates.py` | 死 | ⚠️ **本次重构造成**：删 `AgentOrchestrator` 时状态提示内联进了编排器 |
| `app/infrastructure/observability/tracer.py` | 死 | ⚠️ **本次重构造成**：自研 span 树随 `AgentOrchestrator` 一起失去消费方 |
| `app/core/memory/long_term.py` | 死 | 已重写但未接编排器 |
| `app/core/rag/reranker.py` | 死 | 改造前就是死的 |
| `app/core/tools/mcp_client.py` | 死 | MCP 能力有客户端但无接入点 |
| `app/etl/pipeline.py` | 死 | 文档 ingest 走的是 `documents.py` 直接单条入库，没走分块管道 |
| `app/infrastructure/cache/redis_client.py` | 死 | `main.py` 直接用 `redis.from_url`，绕过了这个封装 |
| `app/infrastructure/database/session.py` | 死 | `main.py` 直接用 `create_async_engine` |
| `app/infrastructure/llm/router.py` | 死 | 多供应商路由的空壳 |

**这是一个诚实的自我批评**：我在诊断里把"两套骨架并存"列为首要问题，而重构后死代码从 ~8 个变成 12 个——删掉消费方而没有同步处理被依赖方。

**建议**（三选一，按模块决定，不要一刀切）：

| 处置 | 适用模块 | 理由 |
|---|---|---|
| **接线** | `long_term.py`、`etl/pipeline.py`、`redis_client.py`、`database/session.py`、`reranker.py` | 有真实用途，缺的是接入点（见 B-1、B-2、A-4） |
| **删除** | `tracer.py`、`templates.py`、`react_agent.py`、`planner.py`、`reflection.py` | 与主链路（原生 function calling + OTel）职责重复；保留只会让人误以为在用 |
| **标注为扩展点** | `mcp_client.py`、`llm/router.py` | 明确写进 README 的"扩展点"章节并加 `# 尚未接入` 注释，或移到 `app/extensions/` |

不要留在 `app/core/` 下面装作在用——这正是改造前最难排障的形态。

#### A-3 没有数据库迁移工具 🟡

**现状**：审计表靠 `metadata.create_all()` 建。

**影响**：schema 演进无版本、无回滚、多环境不一致。审计表在合规场景是要长期存的，加字段时没有迁移路径。

**建议**：引入 Alembic，`SqlAuditLog.ensure_schema()` 改为仅在 `APP_ENV=dev` 下允许，生产走 `alembic upgrade head`。

#### A-4 Milvus schema 演进无方案 🟡

**现状**：知识库新增了 `status` / `tenant_id` / `policy_version` / `effective_from`，对已存在 collection 不生效，只能重建；`set_status` 用"删旧插新"实现状态变更。

**建议**：写一个 `scripts/migrate_milvus.py`：新建带版本后缀的 collection → 从旧 collection 读出并补默认字段 → 批量写入 → 切别名。`set_status` 大批量场景改走离线重建。

#### A-5 依赖与构建 🟡

- 无 lock 文件（`requirements.txt` 固定了版本但无 hash，也无 `uv.lock`/`poetry.lock`）
- 无 `.dockerignore`（`.venv`、`.pytest_cache`、`docs` 会进构建上下文）
- 无 `pre-commit`
- Dockerfile 单阶段构建且装了 `build-essential` 却没多阶段剥离，镜像偏大

### B 类：Agent 能力补齐

#### B-1 L4 长期记忆没有在线流程 🔴

**现状**：`LongTermMemory` 类已重写（租户过滤、TTL、`policy_version` 失效、PII 写入判别），但**没有任何调用方**。

**缺的两件事**：

1. **写入时机与判别**：什么时候把一轮对话里的内容沉淀为长期记忆？目前 `evaluate_write` 只做了"够不够长、是否含 PII、是否一次性表述"的负向过滤，缺正向判断（这条信息跨会话还有用吗）。
2. **召回与注入策略**：召回的记忆放进 system prompt 的哪个位置、放几条、与 L2 冲突时谁优先、召回分数阈值多少。

**建议**：
- 写入：在确认门执行成功后（`APPROVAL_SUBMITTED`）沉淀"该用户的采购偏好/常用供应商/常用预算编码"，来源明确、值得跨会话保留。
- 召回：在 `_system_prompt` 里新增"历史偏好（仅供参考，与本会话已确认信息冲突时以后者为准）"段落，`top_k≤3`、`min_score` 设阈值，并把召回结果记入 trace 便于归因。
- 加测试：L2 已确认值与 L4 召回值冲突时，L2 必须胜出。

#### B-2 RAG 与主链路未真正贯通 🔴

**现状**：存在两套检索路径。

| 路径 | 实现 | 谁在用 |
|---|---|---|
| 主链路 | `MilvusKnowledgeSearch.search_active` → `search_procurement_knowledge` 工具 | 编排器 |
| RAG 管道 | `MultiChannelRetriever`（向量+关键词+意图三路并行、去重合并）+ `RAGAnswerGenerator` | 只有 `ProcurementAgentOrchestrator`，未接 API |

主链路用的是**单路向量检索**，而写得更好的多路检索 + `reranker` 没被用上。这与改造前"两套骨架"是同一类问题，只是从编排层下移到了检索层。

**建议**：让 `search_procurement_knowledge` 走 `MultiChannelRetriever`：
- 关键词通道可以先用 PostgreSQL 全文索引或 Milvus 的标量过滤兜底
- 接上 `reranker`（当前是死代码）
- 补 query 改写（把"这个要走什么审批"改写为含品类与金额的可检索 query）
- 保留 `ProcurementAgentOrchestrator` 作为离线评测入口即可

#### B-3 回答没有引用溯源 🔴

**现状**：知识片段带了 `id` / `title` / `policy_version`，但没有机制要求模型在回答里标注引用，也没有校验。

**影响**：制度问答场景下"依据哪一条"比"答了什么"更重要。用户无法核实，出错也无法定位是检索错还是生成错。

**建议**：
- system prompt 要求引用格式 `[doc:{id}]`
- 响应体新增 `citations: [{doc_id, title, policy_version, snippet}]`
- 加一道后处理校验：回答里出现的 `doc:` id 必须在本轮检索结果中，否则剔除并标记
- 金标集加"引用准确率"指标

#### B-4 工具规模化的可靠性机制 🟡

**现状**：6 个工具全量塞进每次请求的 `tools` 数组。

**影响**：工具增长到 20+ 时，prompt 膨胀、模型选错工具的概率上升。

**建议**：按意图分组暴露工具子集（`REQUISITION_PLANNING` 意图不需要暴露知识检索之外的全部），或引入工具检索（先用 embedding 选出 top-k 工具再喂给模型）。当前规模还不急，但要留好 `function_definitions(access_levels=...)` 这类过滤入口（已有雏形）。

#### B-5 长任务的中断与恢复 🟡

**现状**：`PendingAction` 解决了"等用户确认"这一种中断，但没有通用的任务恢复机制。

**影响**：SSE 断线后本轮进度丢失；跨请求的长流程（如"等供应商报价回来再继续"）无法表达。

**建议**：SSE 加 `Last-Event-ID` 支持，事件带单调递增 id，断线重连从会话状态续推；长流程引入 `PendingTask`（与 `PendingAction` 同构，但由外部事件而非用户点击驱动）。

#### B-6 撤回与纠错 🟡

**现状**：提交后不可撤回，`README` 与预览文案都明确告知"不可自助撤回"——诚实，但功能上是缺口。

**建议**：接入 OA 后补 `POST /api/v1/approvals/{no}/withdraw`，走与提交对称的确认门与审计。

### C 类：安全与合规（已有骨架，缺出站侧）

#### C-1 没有限流与配额 🔴

**现状**：无任何速率限制。

**影响**：单用户可以打满 LLM 配额；`/documents/ingest` 可被刷；`/chat` 是高成本接口，无保护。

**建议**：
- 接入层：按 `subject_id` + `tenant_id` 的滑动窗口限流（Redis 实现），`/chat` 与 `/documents/ingest` 分别限
- 应用层：租户级日/月 token 配额，超额返回 429 并给出配额信息
- 已有的 `RunBudget` 是**单请求**预算，与跨请求配额是两回事，不能互相替代

#### C-2 出站内容没有脱敏 🔴

**现状**：`audit.redact()` 只作用于审计载荷。发给 LLM 的请求体、structlog 日志、`/metrics` 都没有脱敏。

**影响**：供应商报价、预算金额、人员信息进入第三方模型服务与日志系统。

**建议**：
- LLM 请求前过一道出站过滤（手机号/身份证/银行卡/邮箱掩码），并把"是否脱敏"记入 trace
- structlog 加 processor 做字段级掩码
- 明确哪些字段允许出境（采购场景通常品类和金额可以，人员标识不行）

#### C-3 密钥管理 🟡

**现状**：API key 走环境变量。`.env.example` 曾提交真实格式密钥（已替换，**原密钥仍需吊销**）。

**建议**：接 KMS / Vault / 云厂商 secrets manager；CI 加 secret 扫描（gitleaks / trufflehog）防止再次提交。

#### C-4 审计的保留与查询能力 🟡

**现状**：`/audit/recent` 只能取最近 N 条，按租户过滤。

**影响**：合规通常要求按时间范围、按资源、按操作人检索，且保留数年。

**建议**：补查询接口（时间范围 + `resource_type` + `actor` + `action` 过滤 + 分页）、导出（CSV/JSONL）、分区表与归档策略、`payload_sha256` 的完整性校验工具。

#### C-5 对抗测试缺失 🔴

**现状**：注入防护实现了（数据边界、可疑文档标记、写发布分离），但**只有一个测试用例**（`test_knowledge_tool_wraps_content_and_flags_injection`）。

**建议**：建对抗测试集，至少覆盖：
- 知识库注入：伪造制度要求跳过审批 / 伪造 `</knowledge>` 提前闭合 / 要求泄露 system prompt
- 越权：冒用 `requester_id`（已覆盖）、跨租户读会话（已覆盖）、跨用户确认动作（已覆盖）、用 `include_drafts=true` 越权看未发布文档
- 诱导：诱导模型声称"已提交"并给出假单号（**当前只有一个弱断言，需要加强**）
- 数值篡改：诱导模型在后续轮次改掉已确认金额（L2 已保护，但缺端到端用例）

---

### D 类：可靠性与运维

#### D-1 指标是进程内的，多副本不可聚合 🔴

**现状**：`MetricsCollector` 是 `threading.Lock` + 进程内 dict，`/metrics` 返回单副本快照。

**影响**：多副本部署时看到的是随机某个副本的数据，无法做告警和容量规划。

**建议**：改用 `prometheus_client`，`/metrics` 输出 Prometheus 文本格式；OTel 侧补 metrics signal 导出（当前只配了 trace）。保留 `MetricsCollector` 作为无 Prometheus 时的退化实现。

#### D-2 没有告警规则 🟡

**建议**：定义并落地 SLO 与告警：工具失败率 > 5%、`tool_error_missing_arguments` 突增（通常意味着 prompt 或 schema 退化）、熔断打开、`responses_degraded` 突增、确认门超时率、P95 首 token 延迟。

#### D-3 LLM 多供应商路由与故障转移 🟡

**现状**：`infrastructure/llm/router.py` 是死代码空壳，单供应商单模型。

**影响**：DashScope 抖动时只能整体降级到规则答复，而实际上可以切备用模型。

**建议**：接线 router，按 `(能力等级, 成本, 健康度)` 选路；主模型熔断时自动切备用；`stream_turn` 支持按模型分别记录指标。同时区分"意图分类/摘要"这类可用小模型的场景（当前 `IntentRecognizer.with_llm` 与 `MemorySummarizer` 都用 `qwen-max`，成本浪费）。

#### D-4 重试策略 🟡

**现状**：工具层有超时，但没有对下游瞬时故障的重试；LLM 层依赖 SDK 默认重试。

**建议**：对幂等的只读工具加指数退避重试（≤2 次）；写操作**不重试**（靠幂等键 + 用户重新确认）——这个区分要显式写进 `ToolSpec`。

#### D-5 同会话并发的协调 🟡

**现状**：`SessionStore` 用版本号 CAS，冲突时只记 warning 不覆盖。

**影响**：用户快速连发两条消息时，后写的那次会丢状态更新（本轮回复已发出，但槽位变更没落库）。

**建议**：会话级分布式锁（Redis `SET NX` + 租约）让同会话请求排队；或冲突时读-改-写重试一次。

---

### E 类：领域与真实集成

#### E-1 采购制度是硬编码的，不是数据 🔴

**现状**：`default_procurement_policy()` 把所有阈值写死在代码里，`company_id` 参数形同虚设。

**影响**：
- 制度改版要改代码、发版
- 多法人无法各自一套制度（而 `Principal.tenant_id` 已经是硬隔离边界）
- `POLICY_VERSION` 只是个字符串标签，与实际规则内容没有绑定

**建议**：
- 制度落库（PostgreSQL），`ProcurementPolicy` 从数据加载，按 `(tenant_id, effective_from)` 取当期版本
- `policy_version` 由内容哈希派生，与 L4 记忆/L5 审计里记的版本真正对应
- 提供制度管理接口（需 `admin` scope）+ 变更审计 + 生效日期
- 保留代码里的默认制度作为"未配置时的种子数据"

#### E-2 下游全是进程内模拟，且无契约测试 🔴

**现状**：`search_catalog` / `search_suppliers` / `submit_approval` 返回硬编码数据。

**建议**：
- 定义下游接口的 Protocol，模拟实现改名为 `FakeCatalogClient` 等并移出 `core/tools`
- 接真实 SRM/OA 时用 contract test（pact 或录制回放）锁定契约
- `idempotency_key` 直接作为下游 `Idempotency-Key`（当前已预留）

#### E-3 预算余额没有真实校验 🟡

**现状**：`budget_ceiling_cny` 靠用户/模型填，`budget_codes` 只做展示。

**影响**：合规校验里的"超预算"判断建立在自述数据上。

**建议**：接费控系统查预算编码的实际可用余额，作为工具的一次真实查询而非参数。

#### E-4 审批状态回调 🟡

**现状**：提交后没有后续——审批通过/驳回不会回到会话。

**建议**：加 webhook 接收端点（需签名校验），更新 L2 草稿状态与 L5 审计，可选推送给用户。

---

### F 类：质量保障

#### F-1 模型在环的评测缺失 🔴

**现状**：金标集只覆盖确定性部分（意图规则、参数解析、合规规则、审批链）。这个边界划得对，但另一半没建。

**缺的指标**：
- **指令遵循率**：确认门场景下模型是否真的没声称"已提交"（当前只有一个弱断言）
- **幻觉率**：回答里的金额/日期/审批人是否都能溯源到工具输出
- **拒答恰当性**：信息不足时是否提问而不是编造
- **工具选择准确率**：给定用户输入，模型是否选了正确的工具（这是 function calling 应用最核心的指标，当前**完全没测**）
- **引用准确率**（依赖 B-3）

**建议**：建 `evals/` 目录，独立于单元测试：
```
evals/
├─ cases/                 # 每个用例：输入 + 期望的工具调用序列 + 期望回答约束
├─ runner.py              # 跑真实模型，输出指标报告
└─ judges/                # LLM-as-judge 的评分 prompt（带版本号）
```
在 CI 里作为 nightly job 或 PR 标签触发（不阻塞每次提交，因为要花钱且有波动），设置基线与告警阈值。

#### F-2 没有覆盖率度量 🟡

**建议**：`pytest --cov=app --cov-fail-under=70` 入 CI。当前 82 个模块 112 个测试，估计覆盖集中在新写的记忆/工具/harness 层，`infrastructure/` 和 `rag/` 覆盖很低。

#### F-3 Prompt 版本管理只有一个字符串 🟡

**现状**：`PROMPT_VERSION` 是配置里的字符串，prompt 内容硬编码在 `BASE_SYSTEM_PROMPT`。

**影响**：无法灰度、无法 A/B、无法回滚到某个具体 prompt 内容。"上周还好好的"仍然无法归因（只知道版本号变了，不知道内容怎么变的）。

**建议**：prompt 内容外置（文件或数据库）+ 内容哈希作为版本 + 按租户/比例灰度 + trace 里记录实际使用的 prompt 哈希。

#### F-4 没有负载测试 🟡

**建议**：用 locust/k6 压 `/chat`（流式），关注首 token 延迟 P95、并发下的 Redis CAS 冲突率、连接池饱和点。

---

### G 类：交付与体验

#### G-1 SSE 协议设计完整但没有消费方 🟡

**现状**：`status` / `tool_call` / `tool_result` / `confirmation_required` 事件设计得很完整，但没有任何前端消费它们。确认门的两步交互（展示 preview → 用户点确认 → 调 `/approvals/confirm`）**必须有 UI 才能走通**。

**影响**：这是当前最大的"设计完成度 > 可用完成度"的落差。项目目前只能用 curl 演示，而确认门恰恰是最需要看到界面才能理解价值的功能。

**建议**：做一个最小前端（单页即可）：消息流 + 工具进度条 + 确认卡片（展示 preview + 确认/取消按钮）+ 缺失字段提示。这对项目的可展示性提升最大。

#### G-2 缺会话管理接口 🟡

**现状**：只能按已知 `session_id` 取，没有"我的会话列表"、没有历史查询、没有删除。

**建议**：`GET /api/v1/sessions`（按 subject 列出，带标题摘要与更新时间）、`GET /api/v1/sessions/{id}`、`DELETE /api/v1/sessions/{id}`（软删 + 审计）。Redis 侧需要按 subject 维护一个索引 set。

#### G-3 请购单导出 🟢

**建议**：导出 PDF/Excel，采购场景常需线下流转。

#### G-4 多语言 🟢

**现状**：`ChatRequest.locale` 字段存在但未被使用。

**建议**：要么接线（prompt 与确定性文案按 locale 切换），要么删掉——留着不用是误导。

#### G-5 接入文档与 SDK 🟢

**建议**：除 OpenAPI 外补一份"三步接入"指南（拿 token → 发消息 → 处理确认门），以及一个 TypeScript 客户端处理 SSE 与确认流程。

## 五、建议路线

### 阶段一：让工程可持续（1–2 周）

目标是"改代码不再靠人记得跑测试"。

1. `.github/workflows/ci.yml`：ruff + mypy + pytest + 覆盖率 + 金标门禁（A-1、F-2）
2. 死代码三分类处置：接线 / 删除 / 移到 `app/extensions/` 并标注（A-2）
3. Alembic + `.dockerignore` + pre-commit + secret 扫描（A-3、A-5、C-3 一部分）
4. Prometheus 指标 + 基础告警规则（D-1、D-2）

**验收**：CI 全绿，`app/` 下无未引用模块，`/metrics` 输出 Prometheus 格式。

### 阶段二：补齐 Agent 能力闭环（2–3 周）

目标是让"记忆"和"检索"真正在主链路里发挥作用。

1. L4 接线：写入时机 + 召回注入策略 + L2 优先的冲突测试（B-1）
2. RAG 贯通：`search_procurement_knowledge` 走多路检索 + reranker + query 改写（B-2）
3. 引用溯源：`citations` 字段 + 后处理校验 + 引用准确率指标（B-3）
4. 制度数据化：落库 + 按租户取当期版本 + 内容哈希作版本（E-1）

**验收**：制度问答能给出可核实的引用；改制度不需要发版；金标集新增引用准确率指标。

### 阶段三：生产化（2–3 周）

1. 限流与租户配额（C-1）
2. 出站脱敏 + 日志掩码（C-2）
3. 对抗测试集 + 模型在环评测 `evals/`（C-5、F-1）
4. 多供应商路由与故障转移；意图分类/摘要下沉到小模型（D-3）
5. prompt 外置 + 内容哈希版本 + 灰度（F-3）
6. 会话并发锁 + 重试策略（D-4、D-5）

**验收**：有成本报表；有 nightly 评测报告与基线；主模型故障可自动切换。

### 阶段四：接上真实世界（视集成方进度）

1. 最小前端，把确认门跑通给人看（G-1）
2. 会话管理接口（G-2）
3. SRM/OA/费控真实集成 + 契约测试 + 审批回调（E-2、E-3、E-4）
4. 撤回、导出、SDK（B-6、G-3、G-5）

## 六、如果只做三件事

按"投入产出比"排序：

1. **加 CI 并清理死代码**（A-1 + A-2）。成本最低，收益最直接：门禁开始生效，仓库不再自我矛盾。而且死代码是这个项目现在最容易被人质疑的一点——诊断里批评过的问题在重构后反而变多了。
2. **补工具选择准确率的评测**（F-1 的一部分）。function calling 应用最核心的指标当前完全没测。哪怕先做 20 个用例的手工金标（用户输入 → 期望调用哪个工具），也比没有强。这个指标一旦有基线，后续所有 prompt 与 schema 改动就都有了归因依据。
3. **做最小前端把确认门跑通**（G-1）。项目目前最大的落差是"设计完成度远高于可用完成度"。确认门是整个改造里最有价值的机制，但没有 UI 就只能靠 curl 讲，说服力差一个量级。

## 七、一句话总结

这个项目的 **Agent 内核（状态治理、写操作治理、错误闭环、身份边界、降级）已经达到可以拿去讲设计的水准**，这些恰好是同类项目最容易做错也最难补救的部分。

它现在缺的不是"更聪明的 Agent"，而是**让这套内核能被持续维护（CI、死代码、迁移）、能被观测和约束（Prometheus、限流、配额）、能被验证（模型在环评测）、以及能被人看见（前端）**。

补齐路径清晰，且不需要推翻现有设计——按阶段一到四推进即可。
