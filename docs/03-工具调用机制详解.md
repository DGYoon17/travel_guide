# 工具调用机制详解

> **历史文档（采购版）**：本文以采购域 6 个工具为例。差旅域 11 个工具的读写分级、
> 确认门与报价快照见 [04-差旅Agent改造说明.md](04-差旅Agent改造说明.md)。

> 文档范围：ProcureMind AI 项目中的 6 个注册工具、完整调用生命周期、关键机制说明、发现并修复的 bug，以及与评估文档的对应关系。

## 一、当前注册了 6 个工具

全部在 `app/core/tools/builtin.py` 的 `build_default_registry()` 一处声明，按**风险级**分三档：

| 工具 | 风险级 | 需要的 scope | 服务端注入字段 | L2 回填 | 作用 |
|---|---|---|---|---|---|
| `check_procurement_policy` | READ | — | 身份 4 项 | ✅ | 按金额/品类/供应商类型算审批路径、硬性阈值、合规风险 |
| `search_procurement_catalog` | READ | — | — | — | 查集采目录物料与参考价 |
| `search_suppliers` | READ | — | — | — | 查供应商库（合作状态/城市/评分） |
| `search_procurement_knowledge` | READ | `knowledge:read` | — | — | 语义检索制度/SOP/案例原文片段 |
| `plan_purchase_requisition` | DRAFT | `requisition:draft` | 身份 4 项 | ✅ | 生成请购单草稿（明细+总额+审批链+合规提示） |
| `submit_purchase_approval` | **WRITE** | `requisition:submit` | 身份 4 项 | — | 提交审批。**必须先过确认门，不直接执行** |

**"身份 4 项"** = `requester_id` / `requester_level` / `department` / `tenant_id`，这些字段**不出现在模型可见的 schema 里**，执行前由服务端从凭据 + 主数据注入，模型无法冒用。

### 模型实际看到的参数（以 `plan_purchase_requisition` 为例）

```
必填: category(枚举7值) · item_name · unit_price_cny(string) · needed_by(string) · reason
可选: quantity · budget_code · budget_ceiling_cny · supplier_name
      supplier_type(枚举2值) · single_source · urgency(枚举3值) · contract_months
```

## 二、一次工具调用的完整生命周期

以 `plan_purchase_requisition` 为例，从模型吐出 `tool_calls` 到结果回喂的完整路径：

```
① 流式累积
   LLMService.stream_turn 按 index 拼 tool_calls 分片
   （id/name/arguments 分散在多个 chunk，arguments 逐字符到达）
            ↓
② 风险分流
   registry.get(name).needs_confirmation
   WRITE → 走确认门（见第四节）；READ/DRAFT → 直接执行
            ↓
③ scope 校验
   principal.missing_scopes(spec.required_scopes) → 403 类错误
            ↓
④ 参数处理
   registry.parse_arguments()
   a. JSON 解析（坏 JSON → MALFORMED_ARGUMENTS_JSON）
   b. L2 回填：模型漏填的字段用草稿已知值补上
   c. 剔除模型试图自填的身份字段 → 用可信值覆盖
   d. pydantic 校验 + field_validator 宽松解析
            ↓
⑤ 执行
   asyncio.wait_for(handler(args, ctx), timeout=15s)
   只读工具间 asyncio.gather 并发
            ↓
⑥ 回写 L2
   draft_updates → source=INFERRED（模型抽的，待确认）
   draft_facts   → source=TOOL（工具算的）
            ↓
⑦ 观察值
   ToolSuccess.to_observation() / ToolFailure.to_observation()
   作为 role=tool 消息进记忆 → 下一轮喂给模型
            ↓
⑧ SSE + 审计
   tool_call / tool_result 事件推前端；写 L5 事实日志
```

## 三、关键机制说明

### 3.1 宽松解析（第④步的 d）

模型填 `"unit_price_cny": "1.5万"` / `"needed_by": "下周五"` 时，`field_validator(mode="before")` 调 `app/core/tools/coercion.py` 实时转换，**不先失败一轮再让模型改**。

支持的写法：

| 类型 | 示例 |
|---|---|
| 金额 | `15000` / `15,000元` / `￥15000` / `1.5万` / `1万5` / `8千` / `18.8k` |
| 日期 | `2026-09-15` / `明天` / `下周五` / `本周三` / `7天后` / `3个工作日后`(跳周末) / `本月底` / `1月10日`(已过滚明年) |

### 3.2 结构化错误回喂（解析失败时）

错误格式让模型可以照着改，而不是返回无意义的错误码：

```json
{
  "ok": false,
  "error_code": "missing_arguments",
  "message": "调用 plan_purchase_requisition 缺少必填字段：needed_by、reason",
  "field_issues": [
    {
      "field": "needed_by",
      "problem": "Field required",
      "expected": "类型 string；需求到货或上线日期，YYYY-MM-DD；也接受「下周五」「7天后」"
    }
  ],
  "hint": "缺失字段若用户没提供，请直接向用户提问，不要填占位值或猜测的金额与日期。",
  "retry_allowed": true,
  "next_step": "请修正上述字段后重新调用同一工具。"
}
```

`retry_allowed` 由错误码决定：

| 可修复（模型自修正，最多 2 轮） | 不可修复（立即停） |
|---|---|
| `missing_arguments` / `invalid_arguments` / `malformed_arguments_json` / `unknown_tool` / `precondition_not_met` | `permission_denied` / `timeout` / `upstream_error` / `internal` |

超过 2 轮仍不行 → 转成确定性追问：`还需要你补充：- 需求到货/上线日期（格式 YYYY-MM-DD…）`

### 3.3 WRITE 工具的确认门

`submit_purchase_approval` 在②被拦下，**handler 根本不执行**，走如下路径：

```
校验参数
  → 检查前置条件（有草稿？必填齐？没提交过？）
  → spec.preview(args, ctx) 生成确定性摘要
  → 算幂等键 = 租户:主体:请购单ID:草稿指纹
  → 存 PendingAction + 审计 ACTION_PENDING
  → 回给模型: CONFIRMATION_REQUIRED
    （"不要声称已提交，不要给单号"）
  → 中断本轮，回给用户 preview 原文（不让模型润色数字）
```

真正执行只能通过 `POST /api/v1/approvals/confirm {action_id, decision}`——**不经任何自然语言判定**。执行时会再校验草稿指纹，草稿被改过则 409 拒绝。

### 3.4 工具声明是单一真相

`ToolSpec` 一份声明派生出全部行为：

```python
ToolSpec(
    name="plan_purchase_requisition",
    description="...",               # → function.description
    args_model=PlanRequisitionArgs,  # → parameters schema（schema.py 派生）
    handler=_plan_requisition,       # → 执行体
    access=ToolAccess.DRAFT,         # → 是否走确认门
    injected_fields=IDENTITY_FIELDS, # → 从 schema 剔除 + 执行前注入
    required_scopes=(Scope.REQUISITION_DRAFT,),
    draft_backfill=True,             # → L2 回填
    preview=_preview_submit,         # → WRITE 才需要
)
```

`app/core/tools/schema.py` 做三件适配：内联 `$ref`/`$defs`、折叠 `anyOf:[T,null]`、剔除注入字段。同一份 `ToolSpec` 还能导出 MCP catalog（带 `requiresConfirmation` 标注）。

## 四、发现并修复的两个 Bug

### Bug 1：金额字段的 schema 与描述矛盾

**现象**：导出 schema 后发现 pydantic 对 `Decimal` 字段生成：

```json
{
  "anyOf": [
    {"type": "number"},
    {"type": "string", "pattern": "^[+-]?0*\\d*\\.?\\d*$"}
  ]
}
```

这个 pattern **只允许纯数字**，恰好禁止了描述里承诺接受的「1.5万」「8千」。守规矩的模型会因此拒绝发送这些写法，部分做 schema 校验的 API 网关会直接拒绝请求——运行时 `coercion.py` 能解析，但 schema 在骗模型。

**修复**：在 `app/core/tools/builtin.py` 添加 `money_schema()` 函数，通过 `json_schema_extra` 应用到 4 个金额字段：

```python
def money_schema(schema: dict[str, Any]) -> None:
    """把金额字段的 schema 改写成裸 string。
    pydantic 为 Decimal 生成的是 anyOf: [number, string]，且 string 分支带
    ^[+-]?0*\d*\.?\d*$ pattern —— 恰好禁止了字段描述里承诺接受的「1.5万」「8千」。
    """
    schema.pop("anyOf", None)
    schema.pop("pattern", None)
    schema["type"] = "string"
```

受影响字段：`unit_price_cny` / `budget_ceiling_cny` / `estimated_total_cny` / `max_budget_cny`

### Bug 2：`PolicyQuery.amount_cny` 是 float 造成精度往返

**现象**：`Decimal("15000.00")` → `float()` → `Decimal("15000.0")` → `str()` = `"15000.0"`，导致审批路径测试断言 `"15000.00" == "15000.0"` 失败，且金额用 float 本身是精度隐患。

**修复**：`app/core/tools/policy_query.py` 中 `PolicyQuery.amount_cny` 从 `float` 改为 `Decimal`，移除全部 `float()` 转换调用。

```python
# 修改前
amount_cny: float = 0.0

# 修改后
amount_cny: Decimal = Decimal("0")
```

## 六、与评估文档的对应关系

工具层是 `docs/02-完整Agent应用评估与补充路线.md` 评分最高的部分（★★★★☆）。当前两个现状需注意：

### 现状 1：下游是进程内模拟（文档 E-2）

4 个工具的数据源目前是硬编码返回值：

| 工具 | 下游状态 |
|---|---|
| `search_procurement_catalog` | 返回硬编码物料列表 |
| `search_suppliers` | 返回硬编码供应商数据 |
| `submit_purchase_approval` | 生成确定性审批单号（无真实 OA 对接） |
| `search_procurement_knowledge` | 依赖 Milvus 连通，无 Milvus 时 UPSTREAM_ERROR |

### 现状 2：工具选择准确率完全未测（文档 F-1）

当前评测能保证"选对工具后参数一定对"，但无法保证"模型会选对工具"。这是 function calling 应用最核心的指标，也是三个最高优先级补充点之一。

**建议的补充用例结构**（可直接加入 `tests/golden/dataset.py`）：

```python
@dataclass
class ToolSelectCase:
    name: str
    text: str                      # 用户输入
    expected_tool: str             # 期望调用的工具名
    must_not_call: list[str]       # 不应调用的工具（防混淆）
```

示例用例：

| 用户输入 | 期望工具 | 不应调用 |
|---|---|---|
| 「软件采购超过多少需要信息安全评估？」 | `check_procurement_policy` | `plan_purchase_requisition` |
| 「帮我起草一个采购 Figma 的申请，预算 1.5 万」 | `plan_purchase_requisition` | `submit_purchase_approval` |
| 「有没有推荐的设计软件供应商？」 | `search_suppliers` | `search_procurement_catalog` |
| 「帮我查一下公司有没有集采的 MacBook Pro」 | `search_procurement_catalog` | `search_suppliers` |
| 「我想了解一下采购流程的 SOP」 | `search_procurement_knowledge` | `check_procurement_policy` |
| 「提交刚才那个请购单」 | `submit_purchase_approval` | `plan_purchase_requisition` |
